# Asset Passport 서비스 정의 v1.0

작성일: 2026-07-31  
상태: MVP의 제품·UX·기술 범위를 고정하기 위한 기준 문서

## 1. 한 문장 정의

**Asset Passport는 RWA 발행사가 최신 증빙과 사람의 검토 없이 공시를 열지 못하게 하고, 그 공개 준비 결정만 GIWA에서 누구나 검증하게 하는 승인 우선(approval-first) Release Gate다.**

이 서비스의 단위는 ‘토큰’이 아니라 **공개하려는 자산의 Release Package**다.

## 2. 해결하려는 단 하나의 문제

RWA 운영에서 위험한 순간은 토큰 발행 자체보다 **공개 직전**이다.

- 문서는 v3로 바뀌었는데 검토 승인은 v2에 남아 있을 수 있다.
- 필수 증빙이 빠졌는데 담당자는 공시가 가능한지 즉시 알기 어렵다.
- 여러 조직이 검토했더라도 외부 파트너는 최신본·승인자·공개 상태를 독립적으로 확인하기 어렵다.

Asset Passport는 이 문제를 다음 규칙으로 해결한다.

> 최신 문서 버전과 필요한 사람의 승인이 연결되지 않으면 공개 상태로 전이할 수 없다.

AI는 이 규칙 위반을 먼저 찾아 설명한다. 사람은 원문 근거를 보고 결정한다. GIWA는 결정된 사실을 증명한다.

## 3. 서비스가 아닌 것

범위를 넓히면 MVP의 목적이 흐려진다. Asset Passport는 다음을 하지 않는다.

- RWA·증권·수익권 토큰을 발행, 보관, 매매, 중개하지 않는다.
- 투자 권유, 법률 판단, 적합성 판정, KYC를 하지 않는다.
- AI가 승인·반려·공시를 자동 실행하지 않는다.
- 원본 문서, 개인정보, 투자자 목록, 금액을 체인에 기록하지 않는다.

## 4. 핵심 개념 사전

| 용어 | 정의 | 저장 위치 |
| --- | --- | --- |
| Asset | 공시 대상이 되는 자산 운영 단위. 예: 태양광 수익권 프로젝트 | 앱·운영 DB / GIWA에는 ID와 상태만 |
| Release Package | 이번에 공개하려는 문서 묶음과 기준일·버전 | 오프체인 |
| Document Hash | 특정 원본 파일을 식별하는 SHA-256 값 | GIWA 및 앱 |
| AI Release Brief | AI가 만든 위험 신호, 비교 결과, 근거 위치, 다음 행동 제안 | 오프체인 |
| Human Attestation | 검토자가 특정 Release Package를 확인했다는 지갑 기반 결정 | GIWA 이벤트·상태 |
| Disclosure Passport | 외부 검증자가 현재 공개 가능 여부와 해시·승인 이력을 확인하는 공유 가능한 증명 화면 | 공개 웹 화면 + GIWA 조회 |
| Release Gate | 문서·승인 조건을 만족하기 전 공개 전이를 막는 규칙과 UX | 앱 + Asset Registry |

## 5. AI·사람·블록체인의 책임 분리

| 주체 | 입력 | 해야 하는 일 | 하면 안 되는 일 | 결과 |
| --- | --- | --- | --- | --- |
| AI Release Copilot | 문서 메타데이터, 버전, 승인 상태, 필요 시 원문 근거의 제한된 오프체인 분석 | 버전 불일치·누락·승인 단절을 탐지하고 다음 행동을 제안 | 법률 판정, 자동 승인, 자동 공시 | AI Release Brief |
| 검토자 | 원문 근거, AI Brief, 변경점 | 승인 또는 반려를 지갑으로 서명 | AI 결과만 보고 승인 | Human Attestation |
| GIWA Asset Registry | 자산 ID, 최신 해시·버전, 역할별 승인, 상태 전이 | 공개 준비 상태와 이력을 변조 어렵게 기록 | 원본 문서 보관·AI 추론 | 검증 가능한 이벤트 |
| 검증자 | 받은 파일, Passport URL | 해시와 온체인 이력을 대조 | 내부 문서·권한 변경 | 일치/불일치 확인 |

## 6. RWA 토큰과의 관계

### MVP의 결론: Asset Passport는 토큰을 발행하지 않는다

RWA 토큰은 자산의 권리·지분·청구권을 나타낼 수 있는 **외부의 금융/자산 레이어**다. Asset Passport는 그 토큰의 발행·보관·거래 레이어가 아니라, 발행사가 공개하기 전 운영 자료가 최신 승인 상태인지 증명하는 **신뢰 운영 레이어**다.

| 구분 | Asset Passport MVP에서의 역할 | MVP 범위 |
| --- | --- | --- |
| GIWA Sepolia Test ETH | 컨트랙트 배포·상태 전이 수수료 | 필요 |
| 외부 RWA 토큰 (ERC-20, ERC-3643 등) | 향후 연동 가능한 참조 대상 | 발행·거래하지 않음 |
| Asset Passport 자체 토큰 | 필요 없음 | 만들지 않음 |
| 문서/승인 증명 | Asset Registry 이벤트와 해시 | 필요 |

따라서 지금 ERC-20이나 NFT를 추가하면 제품 증명이 강해지지 않는다. 오히려 ‘토큰을 만들었지만 공개 오류를 막았는가’라는 핵심 질문을 흐린다.

향후 실제 사업자가 ‘특정 토큰의 공시 패키지’와 연결하고 싶다면 `externalTokenContract`, `tokenId 또는 classId`를 **참조 필드**로 추가할 수 있다. 그래도 Passport는 그 토큰을 소유·전송·발행하지 않는다.

## 7. 사용자 여정

### A. 운영자: 공시를 준비한다

1. 운영자는 Release Package를 선택하거나 새 버전을 등록한다.
2. 시스템은 문서 해시·버전·기준일을 계산·연결한다.
3. AI Release Copilot이 이전 승인과 최신 버전을 비교한다.
4. 불일치가 있으면 Release Gate는 `차단` 상태와 **한 개의 다음 행동**을 보여 준다.
5. 운영자는 검토자에게 승인 요청을 보낸다.

### B. 검토자: 책임 있는 결정을 한다

1. 검토자는 변경된 문서와 AI가 지목한 근거를 확인한다.
2. 승인 또는 반려를 선택하고 GIWA 호환 EVM 지갑으로 서명한다.
3. 승인 시에만 Registry가 최신 해시와 역할·상태 전이를 기록한다.

### C. 검증자: 공개 상태를 독립적으로 확인한다

1. Passport URL 또는 QR을 연다.
2. 받은 파일의 SHA-256을 계산한다.
3. 최신 문서 해시, 승인자, 상태 전이, GIWA Explorer 이벤트와 대조한다.
4. 일치하면 ‘현재 공개 가능한 자료’, 다르면 ‘재검토 필요’를 확인한다.

### D. 관리자: 연결 환경을 유지한다

1. 지갑·역할·네트워크를 설정한다.
2. AI 공급자(Ollama 또는 HTTPS 보안 릴레이)를 등록·연결 확인한다.
3. AI 에이전트의 실행 범위와 실패를 점검한다.

관리자 여정은 공시 처리 여정의 시작 화면이 아니다. 별도 설정 화면 또는 `/settings` 경로여야 한다.

## 8. 화면 정보 구조

```text
/operate                 기본 운영 화면
  - 현재 막힌/공개 가능한 자산 1건
  - 차단 이유, 책임자, 단일 다음 행동
  - AI 근거와 문서 버전
  - 짧은 현재 상태 표시

/review/:assetId         검토자 승인 화면
  - 변경점·원문 근거·AI Brief
  - 승인/반려 지갑 서명
  - 트랜잭션 성공·실패·Explorer 링크

/settings                관리자 설정 화면
  - 지갑·역할·GIWA 네트워크
  - AI 공급자·모델·연결 상태
  - 에이전트 범위와 실행 이력

/verify/:assetId         외부 검증 화면
  - 현재 공개 가능 여부
  - 파일 해시 대조
  - 승인·상태·GIWA 이벤트
```

`Release workflow` 상세 설명은 `/operate`의 주 콘텐츠가 아니다. 온보딩, 도움말, 피치덱에서 보여 주고 운영 화면에는 현재 단계만 작게 표시한다.

## 9. MVP에서 반드시 증명할 장면

단일 대표 시나리오: **감정평가서 v3가 등록됐지만 검토 승인은 v2에 묶인 태양광 수익권**

1. 운영자가 공개를 시도한다.
2. AI/규칙 엔진이 `v3 미승인`을 찾아 차단한다.
3. 검토자가 원문 변경점과 근거를 확인하고 지갑으로 승인한다.
4. GIWA Asset Registry에 최신 해시·승인·상태 전이가 기록된다.
5. 검증자가 샘플 파일과 GIWA Explorer 이벤트를 대조한다.

완료 기준은 ‘예쁜 화면’이 아니라 아래 네 증거가 같은 사실을 가리키는 것이다.

- 운영 화면의 상태
- 컨트랙트 조회값
- GIWA Explorer 트랜잭션/이벤트
- 공개 검증 화면의 파일 해시 결과

## 10. 현재 MVP의 정의상 공백

| 공백 | 왜 중요한가 | 다음 조치 |
| --- | --- | --- |
| 서비스 정의가 여러 문서에 흩어져 있음 | Asset Passport, Release Gate, 운영 증빙이 혼용됨 | 이 문서를 기준 정의로 사용 |
| 실제 승인·공시 트랜잭션 미연결 | 핵심 약속을 화면 밖에서 증명하지 못함 | GIWA Sepolia 배포 후 대표 시나리오 실행 |
| AI Brief의 근거 위치 미구현 | 검토자가 AI를 신뢰하거나 반박할 재료가 부족함 | 문서 버전 비교와 근거 링크 설계 |
| 공유 Passport URL/QR 미구현 | 검증자가 독립적으로 확인하는 마지막 장면이 약함 | `/verify/:assetId`와 Explorer 링크 구현 |
| 설정과 운영의 경로 분리 미완성 | 관리자 기능이 운영자의 집중을 방해할 수 있음 | MVP는 탭, 다음 단계는 독립 경로로 분리 |

## 11. 제품 성공 기준

운영자가 10초 안에 다음 세 질문에 답하고, 1분 안에 올바른 다음 행동으로 이동해야 한다.

1. 어떤 Release Package가 막혔는가?
2. 최신 문서와 어떤 승인 연결이 끊겼는가?
3. 지금 누가 지갑으로 무엇을 결정해야 하는가?

검증자는 Passport URL에서 파일 해시와 GIWA 이력을 대조해, 별도 계정 없이 현재 공개 가능 여부를 판단할 수 있어야 한다.
