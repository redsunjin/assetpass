# Asset Passport MVP 제품 정렬 분석 보고서

작성일: 2026-07-31  
대상: 현재 `app/` 및 공개 MVP (`/mvp/`)  
판정: **화면을 더 다듬기보다, 제품의 실행 단위와 증명 흐름을 먼저 재구성해야 한다.**

## 1. 이 보고서가 답하는 질문

이번 점검의 질문은 “UI가 보기 좋은가?”가 아니다.

> **운영자가 최신 Release Package를 공시하려 할 때, AI가 위험을 제안하고 사람이 지갑으로 결정한 뒤 GIWA 이력과 공개 검증까지 하나의 사실로 이어지는가?**

현재 답은 **아직 아니다**다. 화면에는 각 조각이 있으나, 한 조각의 결과가 다음 조각의 입력·상태·증거로 이어지지 않는다. 그래서 MVP가 운영 도구보다 기능을 나열한 데모처럼 보인다.

## 2. 제품의 기준 정의

Asset Passport의 실행 단위는 자산 자체나 토큰이 아니라 **Release Package**다.

```text
Release Package
  = 공시 대상 Asset
  + 이번 공개에 사용하는 최신 문서 버전·해시·기준일
  + AI Release Brief
  + 역할별 Human Attestation
  + GIWA 상태 전이·이벤트
```

이 묶음이 준비되지 않으면 공개는 차단되고, 준비되면 누구나 검증할 수 있어야 한다.

| 구분 | 책임 | 결과물 | 현재 MVP 상태 |
| --- | --- | --- | --- |
| AI | 버전·누락·승인 단절을 찾아 근거와 다음 행동 제안 | AI Release Brief | 규칙 기반 시나리오와 선택적 LLM 초안만 있음 |
| 사람 | 원문과 AI 근거를 확인해 승인/반려 결정 | 지갑 기반 Attestation | `personal_sign` 미리보기만 있음 |
| GIWA | 최신 해시·승인·상태 전이를 기록 | Registry 이벤트/조회값 | 컨트랙트는 있으나 UI 미연결 |
| 검증자 | 받은 파일과 Passport·체인 이력을 대조 | 일치/불일치 판단 | 브라우저 해시 대조만 구현 |

따라서 이 MVP는 **RWA 토큰 발행·매매 서비스가 아니다.** GIWA Sepolia Test ETH는 Registry 상태 전이 수수료일 뿐이며, ERC-20/ERC-3643/NFT나 자체 토큰을 지금 추가할 이유가 없다. 향후 외부 RWA 토큰은 `externalTokenContract` 같은 참조값으로만 연결한다.

## 3. 실제 구현과 약속의 차이

| 약속한 제품 흐름 | 현재 구현 증거 | 판정 | 제품에 미치는 영향 |
| --- | --- | --- | --- |
| 자료 등록 → AI 점검 → 검토자 승인 → GIWA 기록 → 공개 검증 | `app/index.html`에 5단계 설명과 앵커 이동이 있음 | 설명은 있으나 상태 기계가 아님 | 단계 버튼을 눌러도 Release Package가 진행되지 않음 |
| AI가 최신 문서와 승인 연결을 분석 | `app/app.js`는 선택된 가상 자산의 `aiReview` 또는 메타데이터 기반 LLM 초안을 표시 | 부분 구현 | 실제 문서 비교, 근거 위치, 실행 이력이 없음 |
| 검토자가 책임 있게 승인 | `signReview()`는 `personal_sign`으로 “미리보기” 메시지를 서명 | 미구현 | 승인 뒤 상태가 바뀌지 않고 GIWA 이벤트도 없음 |
| GIWA가 상태를 증명 | `AssetRegistry.sol`은 등록·문서 제출·검토·공개 상태 전이 구현 | UI 미연결 | 화면의 ‘증명됨’은 실제 트랜잭션 증거가 아님 |
| 외부 검증자가 독립 확인 | SHA-256 파일 비교는 동작 | 부분 구현 | Passport URL·현재 체인 상태·Explorer 이벤트가 한 화면에 결합되지 않음 |
| AI 공급자를 운영자가 관리 | 공급자 등록·선택·연결 확인은 있음 | 부분 구현 | 어떤 공급자가 어떤 Brief를 만들었는지 Release Package에 남지 않음 |

## 4. 현재 화면의 근본 문제

문제는 Manager control room과 Release workflow가 한 HTML 문서에 있는 것만은 아니다. 더 큰 문제는 **업무 단위(Release Package) 대신 설명 단위와 설정 단위가 화면의 중심을 차지한다는 점**이다.

현재 기본 운영 화면에는 다음이 동시에 있다.

1. 제품 소개와 제한 고지
2. Gate 상태와 행동 버튼
3. 상세 5단계 Release workflow
4. AI·사람·GIWA 구조 설명 카드
5. 자산 시나리오 선택과 상세 패널
6. 파일 검증·서명 미리보기

각 요소는 개별적으로 틀리지 않지만, 운영자는 이 중 무엇을 먼저 해야 하는지 스스로 골라야 한다. 특히 workflow는 제품 설명에는 유용하지만, 실행 중인 사건을 처리하는 화면의 첫 순서가 되어서는 안 된다.

| Before | After | Why |
| --- | --- | --- |
| 자산 목록·제품 설명·설정이 판단 단위처럼 보임 | `Release Package #RP-2026-001` 한 건을 기본 단위로 표시 | 운영자는 ‘어느 자산인가’보다 ‘이번 공개를 통과시킬 수 있는가’를 결정해야 함 |
| 5단계 workflow가 큰 탭/본문으로 노출 | 상단에 작고 읽기 전용인 현재 상태 표시만 유지, 상세 설명은 도움말·피치덱으로 이동 | 업무 화면에서 설명 탐색이 행동을 앞서면 집중이 무너짐 |
| “검토자 승인으로 이동”이 서명 미리보기로 끝남 | 변경점 → AI 근거 → 승인/반려 → 트랜잭션 결과를 한 승인 화면에 연결 | 버튼의 결과가 다음 시스템 상태를 바꿔야 사용자가 도구를 신뢰함 |
| AI 공급자가 전역 설정값 | 각 Brief에 `provider`, `model`, `runAt`, `inputScope`, `promptVersion`, `resultHash`를 기록 | 누가 어떤 도구로 어떤 제안을 만들었는지 검토·감사할 수 있어야 함 |
| 파일 해시 대조만 제공 | Passport에서 현재 상태·문서 해시·승인자·GIWA 이벤트·Explorer 링크를 함께 제공 | 검증자는 내부 화면을 이해하지 않고도 한 사실을 독립 검증해야 함 |

## 5. 권장 사용자 여정과 화면 경계

### A. 운영자 — `/operate`

목표는 설명을 읽는 것이 아니라 **차단된 Release Package 한 건을 다음 책임자에게 넘기는 것**이다.

```text
차단된 RP 선택
→ AI가 지목한 단 하나의 차단 사유 확인
→ 검토자에게 승인 요청
→ 승인 결과/트랜잭션 수신
→ 공개 가능 상태와 Passport 생성
```

첫 화면에 필요한 것은 다섯 가지뿐이다.

1. `공시 차단` 또는 `공개 가능` 상태
2. 대상 Release Package와 최신 문서 버전
3. 차단 사유 한 문장
4. 책임자와 단일 다음 행동
5. AI → 사람 → GIWA → 검증의 짧은 상태 표시

### B. 검토자 — `/review/:releasePackageId`

```text
AI Brief 확인
→ 바뀐 문서/근거 위치 확인
→ 승인 또는 반려
→ 지갑 트랜잭션 대기·성공·실패 확인
```

여기서만 지갑 서명 버튼을 보인다. 운영 화면에서 지갑 서명 미리보기를 먼저 보여 주지 않는다.

### C. 관리자 — `/settings`

```text
지갑·역할·GIWA 네트워크 확인
→ AI 공급자/모델 연결 확인
→ 에이전트 정책·실행 실패 확인
```

설정은 초기 연결과 장애 대응 화면이다. 현재 사례의 공개 상태 레일은 설정 화면에 둘 이유가 없다.

### D. 검증자 — `/verify/:passportId`

```text
Passport 열기
→ 현재 공개 가능 상태 확인
→ 파일 SHA-256 대조
→ 승인자·GIWA 이벤트·Explorer 링크 확인
```

로그인·지갑·관리 화면 없이 동작해야 한다.

## 6. AI 공급자와 블록체인 관계

AI 공급자는 지갑과 비슷하게 **연결·선택·실행·추적**되어야 하지만, 권한을 갖는 주체는 아니다.

```text
AI provider profile
  └── 선택한 모델로 Release Package 메타데이터/허용된 원문 근거 분석
        └── AI Release Brief 생성 (오프체인)
              └── 사람이 Brief와 원문을 검토
                    └── 지갑으로 승인/반려
                          └── GIWA에는 해시·역할·결정·상태만 기록
```

### AI 공급자 프로필에 필요한 최소 필드

| 필드 | 목적 |
| --- | --- |
| `providerId`, `name`, `kind` | Ollama / HTTPS 보안 릴레이 / 규칙 엔진을 구분 |
| `endpoint`, `model` | 연결 대상과 모델 식별 |
| `dataScope` | 원문·메타데이터·근거 위치 중 무엇을 보냈는지 명시 |
| `connectionStatus`, `lastCheckedAt` | 실제 연결 상태 확인 |
| `policyVersion`, `promptVersion` | 어떤 규칙으로 결과가 만들어졌는지 추적 |
| `runId`, `releasePackageId`, `resultHash` | 특정 Brief를 특정 Release Package에 귀속 |

API 키는 브라우저/로컬 스토리지에 저장하지 않는다. 외부 공급자는 서버 측 보안 릴레이가 키를 관리하며, 로컬 Ollama는 `localhost`만 허용한다. 단, 현재 MVP의 LLM 실행은 문서 원문이 아니라 메타데이터만 분석하므로 **문서 내용의 차이를 분석한다는 표현은 아직 사용할 수 없다.**

## 7. 하네스 평가: 왜 반복 개선이 제품 개선으로 이어지지 않았는가

`scripts/agent-harness.sh`는 이번 실행에서 통과했다.

- 정적 파일/데모 데이터/Pages 동기화 확인
- JavaScript 문법 확인
- AssetRegistry 정적 안전성 확인
- Foundry 컨트랙트 단위 테스트 3개 통과

그러나 현재 하네스는 다음을 검증하지 않는다.

| 확인하는 것 | 확인하지 않는 것 | 결과 |
| --- | --- | --- |
| `personal_sign`, `wallet_switchEthereumChain` 문자열이 UI에 있음 | 승인 버튼이 Registry `reviewLatestDocument` 트랜잭션을 보내는가 | ‘지갑 연결됨’이 실제 온체인 승인처럼 보일 수 있음 |
| HTML/JS/CSS가 존재하고 동기화됨 | 운영자 → 검토자 → 검증자 여정이 상태 전이를 끝까지 통과하는가 | UI를 추가해도 핵심 업무 완료율을 알 수 없음 |
| 컨트랙트 함수와 단위 테스트 | 브라우저가 배포 주소를 읽고 상태/이벤트를 표시하는가 | 컨트랙트와 화면이 독립적으로만 정상임 |
| 해시 계산 코드 존재 | 검증 화면이 실제 Passport와 최신 GIWA 이벤트를 대조하는가 | 파일 비교가 제품 증명까지 이어지지 않음 |
| AI 공급자 입력 검증 | 공급자 실행 결과가 특정 Brief/승인 판단에 추적되는가 | AI 관리가 설정 데모에 머무름 |

이것이 반복적인 UI 변경이 개선으로 체감되지 않은 핵심 이유다. **하네스의 완료 조건이 ‘기능 조각의 존재’이고, 제품의 완료 조건은 ‘한 건의 Release Package가 증명 가능한 상태로 전이’이기 때문이다.**

## 8. 현행화할 완료 기준 (Definition of Done)

다음 대표 사례 하나가 브라우저와 GIWA에서 끝까지 재현되어야 한다.

> 태양광 수익권의 감정평가서가 v2에서 v3로 바뀌었지만, 검토 승인은 v2에 묶여 있다.

| 단계 | 통과 증거 | 실패하면 보이는 상태 |
| --- | --- | --- |
| 1. Release Package 등록 | v3 해시·기준일·필수 증빙이 화면과 Registry에 존재 | 자료 부족/초안 |
| 2. AI Brief 생성 | 공급자·모델·실행 시각·위험 근거·다음 행동이 RP에 귀속 | AI 실행 실패 또는 근거 부족 |
| 3. Gate 차단 | `v3 미승인`과 검토자 요청이 운영 화면에 표시 | 공개 버튼 비활성 |
| 4. 사람 승인 | 검토자가 지갑으로 `reviewLatestDocument`를 호출하고 tx hash 수신 | 서명 취소/권한 없음/체인 오류 |
| 5. GIWA 공개 증명 | 승인 이벤트 후 `markDisclosed` 가능, Explorer 링크 표시 | 조건 미충족으로 상태 전이 거부 |
| 6. 공개 검증 | Passport에서 파일 해시·승인자·이벤트가 일치 | 불일치 → 재검토 필요 |

## 9. 개선 로드맵

### P0 — 제품 단위와 화면 경계 고정 (다음 UI 변경 전에 수행)

1. 데이터 모델에 `ReleasePackage`와 `AIReleaseBrief`의 귀속 관계를 명시한다.
2. 상세 Release workflow와 3단 구조 소개 카드를 운영 기본 화면에서 제거하고 도움말/피치덱으로 옮긴다.
3. 운영·검토·설정·공개 검증을 최소한 논리적 라우트 또는 명확한 전환 화면으로 분리한다.
4. 하네스에 ‘기본 운영 화면에서 차단 사유·책임자·단일 행동이 보이는지’ 정적/브라우저 검사를 추가한다.

### P1 — 실제 증명 흐름 연결 (테스트넷 배포 직후)

1. `registryAddress`를 배포 주소로 채우고 ethers/viem 등으로 Registry 읽기/쓰기를 연결한다.
2. `personal_sign` 미리보기를 `reviewLatestDocument` 트랜잭션으로 교체한다.
3. tx hash, 영수증, 이벤트, Explorer 링크를 승인 화면과 Passport에 표시한다.
4. 대표 Release Package 한 건의 차단 → 승인 → 공개 → 검증을 E2E 테스트/수동 점검 시나리오로 고정한다.

### P2 — AI가 감사 가능한 보조자가 되도록 강화

1. AI 실행 결과를 Brief로 저장하고 공급자·모델·입력 범위·결과 해시를 남긴다.
2. 허용된 오프체인 원문에서 변경점과 근거 위치를 추출하는 방식·보관 정책을 확정한다.
3. 공급자 변경 이력, 연결 실패, Brief 생성 실패를 관리자에게 알린다.

### P3 — 외부 검증 경험 완성

1. 공유 가능한 Passport URL/QR을 생성한다.
2. 검증 화면에서 계약 조회와 Explorer 이벤트를 직접 연결한다.
3. 외부 RWA 토큰은 필요할 때만 참조 필드로 연동하고, 발행/보관/거래는 범위 밖으로 유지한다.

## 10. 지금 하지 말아야 할 것

- 화면에 또 다른 설명 카드·탭·에이전트 이름을 추가하지 않는다.
- ERC-20/NFT/자체 토큰을 추가하지 않는다.
- AI가 문서 자체를 분석하거나 법률 판단을 하는 것처럼 표현하지 않는다.
- 테스트넷 트랜잭션 없이 ‘GIWA 증명 완료’로 보이게 하지 않는다.

## 결론

현재 MVP는 **좋은 구성요소를 가진 프로토타입**이지만, 아직 Release Package를 끝까지 처리하는 제품은 아니다. 개선의 순서는 디자인 정리가 아니라 다음과 같아야 한다.

```text
Release Package 정의 고정
→ 운영/검토/설정/검증 화면 경계 확정
→ 실제 GIWA 상태 전이 연결
→ AI Brief 추적성 추가
→ Passport 공개 검증 완성
```

이 기준을 통과하면 Asset Passport는 “AI와 블록체인을 넣은 RWA 대시보드”가 아니라, **잘못된 공개를 차단하고 책임 있는 결정을 증명하는 Release Gate**가 된다.
